One family, four projects

Three device services — Go, Rust, and a PC-local agent — plus the shared web frontend & API spec that keeps them one product.

Rust The in-process build

mibee-eye-rs

Native V4L2 capture and fully in-process encoding — V4L2 M2M hardware with automatic openh264 fallback, zero subprocesses. A ~2 MB static binary for the most constrained boards, OSD watermark burned into every output, and an optional GB 35114 A-level security build.

  • Rust 1.88+
  • ~2 MB static
  • zero subprocess
  • M2M + openh264
  • GB 35114 opt-in
View on GitHub
Go The quickest path

mibee-eye-go

Pure Go, zero CGO — stock cross-compilation out of the box. Three capture profiles: libcamera CSI on Raspberry Pi, generic V4L2 / USB-UVC on any board, and rtsp gateway mode that re-publishes an existing stream as an ONVIF/GB28181 device from any box. HLS browser playback and an i18n web UI included.

  • Go 1.26
  • zero CGO
  • libcamera · UVC · rtsp
  • HLS
  • i18n UI
View on GitHub
Rust The PC-local agent

mibee-eye-notebook

Turns the webcam and microphone of the PC in front of you into a privacy-first local capture agent: a TLS-gated web UI as the primary control surface, outbound streaming default-off. On-device intelligence — a voice assistant (wake word → transcription → local LLM → TTS), object & sound-event detection, OCR, and VLM alarm descriptions.

  • Rust workspace
  • TLS web UI
  • voice assistant
  • fail-open AI
  • resource-adaptive

mibee-eye-webui

One zero-build, zero-dependency ES-module frontend and one SPEC v1 API contract shared by the whole family. The UI renders panels from each device's announced capabilities; a spec-conformant mock server lets you develop the frontend without any hardware.

What every MiBee Eye camera speaks

One capture pipeline fans out to every standard a camera is asked to speak — NVRs discover it, platforms register it, browsers manage it.

GB/T 28181-2022 device

SIP registration over UDP, TCP (inbound or device-dialed) or SIPS/TLS with negotiated expiry and redial; paginated Catalog/RecordInfo answers plus the 2022 five info queries; live/playback/download over RTP·PS or ES-over-RTP (TCP passive/active, multicast); talkback and voice broadcast; alarm/position NOTIFYs; graceful deregistration (Expires:0) on shutdown.

GB 35114 A-level, opt-in

SM2 certificate REGISTER authentication plus keyed-SM3 integrity — the 35114 security profile rides the same GB28181 stack as a build feature.

ONVIF Profile S + Media2

Device / Media / Imaging / PTZ SOAP services, Media2, Pull-Point & push events, WS-Discovery auto-discovery. Tested against Synology Surveillance Station, Blue Iris, Scrypted — and any ONVIF NVR.

RTSP · RTMP · substream

H.264 RTSP server (RTP over TCP or UDP), a low-bitrate substream for narrow links, RTMP push to cloud services, and HLS browser playback in the Go build — all tapping the same encoded frames.

Recording & playback

Continuous segments with an index, retention and storage caps, and the archive doubles as the GB28181 playback source — the platform can seek your local history.

On-device AI, fail-open

NanoDet object detection taps shared pre-encode frames and never blocks the pipeline; a missing model honestly degrades the capability instead of fabricating detections. The notebook agent adds sound events, OCR, VLM descriptions and a voice assistant.

Rust or Go — which one should I use?

Same protocols, same SPEC v1 web UI, same NVR interoperability — pick by deployment profile.

Pick the Go build when… Pick the Rust build when…
GoYou want the quickest path: zero-CGO build, stock cross-compile RustThe board is memory / flash constrained (~2 MB binary)
GoYou want HLS browser playback out of the box RustYou want the OSD watermark burned into every output
GoYou need the i18n UI or the runtime metrics API RustYou want capture + encode fully in-process (no subprocesses)
GoYou prefer hacking on a Go codebase RustYou prefer hacking on a Rust codebase

Both ship AI detection (NanoDet, opt-in), GB 35114 A-level (opt-in), continuous recording with GB28181 playback, imaging controls and snapshots. And when the "camera" is simply the PC on your desk — that's mibee-eye-notebook.

Powered by open protocol libraries

The protocol heavy lifting is extracted into reusable libraries — wire formats pinned by golden tests, built test-first, and available for your next device.

Rust

gb28181-rs

GB/T 28181 device-side library — SIP REGISTER/INVITE over UDP/TCP/SIPS, MANSCDP XML, RTP·PS, subscriptions & NOTIFY, 35114 auth.

 Go

gb28181-go

GB/T 28181 in Go — the device/ UAC consumed by the camera, plus the platform/ UAS powering NVR-side projects: registry, PS/ES demux, INVITE/BYE sessions, cascade, and audio-only pickup channels (type-136 voice inputs).

 Rust

onvif-rs

ONVIF Device service in Rust — SOAP/XML, WS-Discovery, Profile S surface.

 Go

onvif-go

ONVIF client + server in Go — the same engine behind the Go camera's device service.
